# maus-crepe-insights

This is the **canonical, tool-agnostic rulebook** for everyone working in this repo, human or AI
agent (Claude Code, Codex, Cursor, and others). Codex and Cursor read `AGENTS.md` by default;
Claude Code imports it from `CLAUDE.md`. Edit shared rules here, in one place.

BaselHack 2026 project on the Maus Robotics challenge: turning crêpe robot run data (phases, logs,
vision checks with images, recipe parameters, video) into insight on why runs fail and what to
change.

- **GitHub:** https://github.com/leonardoAB1/maus-crepe-insights
- **Team repo:** several people push here. Never rewrite shared history.
- **Public repo:** the code is public, the Maus data is not (see Data handling).

## Stack

- **Language:** Python (>= 3.11, pinned to 3.12 in `code/.python-version`)
- **Package manager:** uv only (`uv sync`, `uv run`, `uv add`) - never pip. Run it from `code/`.
  Commit `code/uv.lock` with every dependency change
- **Lint and format:** ruff (`uv run ruff check .`, `uv run ruff format .`)
- **Tests:** pytest (`uv run pytest`)
- **Build backend:** hatchling (`code/pyproject.toml`)
- **Dashboard access:** MCP over HTTP at `https://dash.mausrobotics.com/mcp` (protocol
  2026-07-28, OAuth with PKCE). See `code/maus_export/client.py`

## Standards

- **Data: MCAP, ROS 2 profile.** Multimodal robot data is stored as MCAP (`ros2msg` schemas,
  `cdr` messages). Prefer standard ROS 2 message types (`rcl_interfaces`, `sensor_msgs`,
  `std_msgs`) and only add `maus_msgs` types when none fits. Document every topic in
  `documentation/mcap.md`
- **Models: ONNX.** Train with any framework, but every shipped model is exported to `.onnx` and run
  with `onnxruntime`, with a model card next to it. See `code/models/README.md`
- **Tables:** flat analysis tables are Parquet (CSV only as a convenience copy)
- **Time:** all stored timestamps are UTC. Robot logs are naive local time (Europe/Zurich); convert
  them, never mix the two

## Layout

The BaselHack template structure is required by the jury. Keep it.

```
code/              # all code
  maus_export/     # dashboard -> raw JSON -> MCAP / tables (importable package)
  models/          # one folder per model: model.onnx, model.json, train.py
  tests/           # pytest suite only - must run offline, without dashboard access
documentation/     # data description, formats, diagrams
assets/            # pitch slides, videos, images
data/              # local exports, gitignored
worktrees/         # git worktrees, gitignored
```

- Reusable logic goes in `code/maus_export/` (or a new package next to it), not in one-off scripts
- Notebooks are fine for exploration; anything the team relies on moves into a package with tests
- Tests use synthetic data shaped like real dashboard responses. Never commit real run data as
  fixtures

## Data handling

- Raw dashboard data, check images, videos, MCAP files and derived tables stay in `data/` and are
  never committed. Do not paste real run data, contacts or supplier details into issues, PRs or
  docs beyond aggregate numbers
- Tokens live in `~/.maus-export/` or the `MAUS_TOKEN` env var. Never commit secrets or `.env`
- Dashboard tools that write (`*_save`, `*_delete`) are off-limits unless the user asks for that
  write in the current session. Reading is fine
- Never send commands to a robot

## Code style

- Type hints on all public functions; small focused modules
- 80 characters per line, enforced by ruff. Docs and comments wrap at 80 too
- Name magic numbers as constants. No bare numbers in logic
- Comments only when the WHY is non-obvious
- **ROS 2 nodes:** any file that defines a ROS 2 node ends in `_node.py`, and only node files use
  that suffix
- **No assistant or tool attribution** anywhere: no "Generated by", "Made with", badges, bylines,
  or `Co-Authored-By:` trailers in code, docs, commits, PR descriptions or issues

## Writing style

- **No em dashes.** Use a regular hyphen (-) if a separator is needed. This applies to commit
  messages, PR descriptions, code comments, docstrings and docs

## Git and PR workflow

**Everything goes through pull requests.** No direct pushes to `main`, for anyone.

1. Open (or pick) a GitHub issue describing the change
2. Create a branch named `type/issueNumber-short-description` (e.g. `feat/3-failure-model`,
   `fix/7-token-refresh`) in its own worktree (see below)
3. Commit in small logical steps using Conventional Commits
4. Push and open a PR that references the issue (`Closes #N`). Fill in what changed, why, and how
   it was tested (offline tests, live dashboard run, or both)
5. At least one teammate reviews. Ruff and pytest must pass
6. **Squash merge** into `main` (the only merge strategy). Delete the branch after merge

Stacked PRs (a branch based on another open PR) are fine when changes depend on each other. Say so
in the PR description and merge in order.

### Commit messages

Conventional Commits. Every commit message must:

- Be a single sentence, lowercase, no period at the end
- Use the format `type: short description`
- Never include AI/tool signatures, co-author lines or attribution footers

**Allowed types:** `feat` (new capability), `fix` (bug fix), `chore` (tooling, config,
dependencies), `style` (formatting, no logic change), `refactor` (restructuring without behavior
change), `docs` (documentation), `perf` (performance), `test` (adding or updating tests).

```
feat: add failure classifier exported to onnx
fix: convert robot log timestamps to utc
chore: add ruff and format code to 80 columns
test: cover mcap round trip with synthetic run
```

## Worktree convention

Every non-trivial change is developed in a dedicated git worktree so branches never share a dirty
working tree.

Worktrees live in a gitignored `worktrees/` folder at the repo root. One folder per branch type,
and inside it the branch leaf (the part after `type/`). Branch `feat/5-dashboard` checks out at
`worktrees/feat/5-dashboard`.

```
maus-crepe-insights/           <- main repo folder, stays on main, only used to pull
maus-crepe-insights/worktrees/ <- gitignored
  feat/
    5-dashboard/               <- branch feat/5-dashboard
  fix/
    7-token-refresh/           <- branch fix/7-token-refresh
```

Create (always from the main repo folder, never from inside another worktree):

```
git switch main && git pull
git worktree add -b feat/5-dashboard worktrees/feat/5-dashboard main
```

Each worktree has its own `code/.venv`; run `uv sync` in `code/` inside it. `data/` is per
worktree too; point `maus-export --data-dir` at the main folder's `data/` to share one export.

Remove after the PR is merged:

```
git worktree remove worktrees/feat/5-dashboard
git branch -D feat/5-dashboard
```

(`-D` is needed because squash merges do not keep the branch commits in `main`.)
