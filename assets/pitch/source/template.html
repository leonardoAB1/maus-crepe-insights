Maus robots make crêpes by themselves and log every run: phases, logs, about 110 recipe settings, camera checks and video. We are the CrêpeFlow Team, and in one line: we turned those logs into measurements, and the measurements into concrete next steps for Maus.

The problem

Why do crêpe runs fail?

Nobody can tell: a failed crêpe comes with a verdict, not a reason

79%

of failed runs cannot be explained from the data. Where a check exists, it is still only pass or fail.

Source: documentation/system/crepe-stages.md, runs table (828 runs, 3 robots)

Of 430 runs that started a crêpe, 147 did not succeed. For 116 of those there is no check data at all, so nobody can say why they failed. And where a check exists, the robot records only pass or fail plus a short message. No measurement, no direction to change. That gap is what we worked on.

The robot

What does the robot see, and what does it decide on its own?

One robot, one Pi, a camera over the hotplate

A run, about 3.5 minutes; the crêpe is served after about 2.5. Orange = a camera check with an image.

Source: documentation/system/system.md, documentation/system/crepe-stages.md

Quick picture of the machine. Everything runs on a Raspberry Pi with ROS 2: a camera looks down at the hotplate, two Duet boards drive the motors and heaters, and every run is uploaded to Maus's dashboard. We only read from that dashboard; we never send anything to a robot. Each run goes prep, bake, serve, reset, and the camera checks the plate, the spread, both folds and the push-off. A failed check does not stop the run: the result is only decided at the very end. That is why the failure reason gets lost.

  2. Each setting's effect is measured on its own, including its sweet spot.

Why a Definitive Screening Design (DSD)

19 runs, not 729

Testing every combination of 6 settings at 3 levels takes 36 = 729 runs.

Each setting on its own

No effect is mixed up with another setting or with a curve: their correlation in the design is 0.

Sweet spots visible

Three levels show whether the best value lies inside the range; 3 centre runs measure run-to-run noise.

Source: documentation/analysis/doe.md, code/maus_export/doe.py

This is where control theory comes in. The robot is a plant in a run-to-run loop: settings go in, quality comes out once per batch, and today a person closes that loop by trial and error. We use a Design of Experiments, specifically a Definitive Screening Design (Jones and Nachtsheim, 2011): 19 runs instead of 729 for every combination. Each setting's effect, and its sweet spot, is measured on its own. In control terms, this is system identification of the run-to-run loop. We never send commands to a robot; it is a run sheet Maus runs by hand.

How do we measure the runs that recorded nothing?

Where the numbers run out, we gave the robot better eyes

The robot already draws its analysis

  • crêpe outline
  • holes

We read those marks back per run: diameter, centre offset, circularity, bare plate, residue, fold overlap, fold 2 / fold 1 area ratio and browning. A distilled segmentation model gives the same view on live video.

Data took us far, but 116 of 147 failures carry no numbers at all. So step two: vision. We export runs read-only into ROS 2 MCAP files and one table with 177 fields per run. The robot already paints its analysis on each check image, so we read those marks back as numbers. For live video, we distilled SAM 3 into a small segmentation model.

What comes next

  • Train on the 186 phase labels and 113 masks we already collected, so models learn from people, not only robot verdicts.
  • Train across more robots, so every check holds up on a robot the model has never seen.
  • Record check stills on every run: today 138 of 828 runs have vision metrics.
  • Add a material and hole mask, so the deviation check runs on real predictions.
  • Time the pass/fail check heads per frame on the Pi 5; the per-frame pipeline already runs at 0.15 s.
  • Rerun all numbers with Maus: the code and tests are public, the run data stays private.
